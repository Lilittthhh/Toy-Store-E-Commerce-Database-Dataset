# Admin Audit Trail — deployment and data boundary

Migration 005 is prepared but **must be reviewed and applied separately**. Do not set `AUDIT_TRAIL_ENABLED=true` until the migration has been approved and the `public.audit_logs` table exists. The default is `false`; while disabled, the Admin page reports that deployment is pending and no audit-table writes occur.

The migration only creates `public.audit_logs` and its indexes. It does not update imported Toy Store rows, alter canonical views, or touch Migration 004. Apply it with the project's reviewed migration procedure, then set `AUDIT_TRAIL_ENABLED=true` and restart FastAPI. Do not run tests that require Migration 005 against the live database until it is applied. The opt-in read-only integration checks require both `RUN_DB_INTEGRATION_TESTS=1` and `RUN_AUDIT_005_TESTS=1`.

Successful allowlisted mutations and meaningful authenticated GET views insert an event on the same pooled PostgreSQL connection immediately before the request commits. If the audit insert fails, that request rolls back. Failed logins are exceptional because the existing lockout counter intentionally commits before the authentication error; a separate best-effort anonymous event records the failure without an attempted identifier or password.

View events include dashboard, analytics/report, staff/customer lists and details, catalog/product, order/refund, saved customer resources, cart, order history, and the Admin Audit Trail itself. A pure view has NULL old/new values; detail IDs come from typed route parameters. Search terms, query strings, and result bodies are not captured. Each successful routed request produces at most one event even if its service performs multiple queries. Separate user-facing resource requests may produce separate, differently named view events. Authentication `/me` refreshes, health, static assets, notification configuration, notification-status helpers, and refund-eligibility helpers are excluded to avoid framework/polling noise. There is no automatic polling added for audit logging.

The audit writer uses a strict allowlist for JSON state changes. Only known status, role, availability, quantity, and row-version values are stored. It never copies request bodies, authentication tokens, passwords, reset codes, payment details, notification credentials, or arbitrary customer text. Descriptions and actor labels are generated by the server; the direct socket peer IP is validated before storage, without trusting client-supplied forwarding headers. User-agent is intentionally not captured to minimize personal data. Entity IDs are populated where available and are not fabricated.

Only Admin has `GET /admin/audit-logs` and `GET /admin/audit-logs/{audit_log_id}`. These support filters and pagination and return newest events first. No audit mutation endpoint exists. Operations Staff and Analyst receive 403, while unauthenticated or customer credentials are rejected by staff authentication. The Streamlit Audit Trail entry is Admin-only; the API remains the authority.
